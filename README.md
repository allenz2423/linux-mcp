# Linux MCP

`linux-mcp` is a standalone MCP server for Linux host inspection and desktop observation/control. It communicates with MCP clients over stdio and combines bounded Linux inventory, a general confirmed shell and interactive PTY sessions, resolver configuration, explicitly confirmed audio endpoint, package, process, container, local and remote QEMU/libvirt VM, virtual-network, and storage inventory/control, supported service-manager and systemd timer, OpenRC runlevel startup, systemd boot and time configuration, power, NetworkManager profile, rfkill radio, cached Bluetooth device inventory and pairing, route, and firewall controls, alongside compositor-aware windows, workspaces, displays, screenshots, accessibility, input, applications, clipboard, and notifications.

It is a separate project inside this repository. Adam is not required to run it. The Python import namespace remains `wayland_mcp` for compatibility.

## Features

- Runs arbitrary `/bin/sh` commands after MCP client confirmation bound to the complete request. Commands use the server process's Linux identity by default; optional root mode uses noninteractive `sudo` when configured. Time, output, stdin, and environment overrides are bounded; this one-shot command tool uses pipes without a TTY.
- Starts persistent interactive `/bin/sh` sessions on PTYs after exact-request confirmation. Read, write, resize, and close operations are separate tools; every input or resize needs its own confirmation. Sessions are limited to 8 concurrent processes, 30 minutes each, and 1 MiB retained output apiece.
- Reads paged binary file ranges and creates, atomically replaces, or appends binary files after exact confirmation. Single-call writes support up to 4 MiB; confirmed sequential uploads support atomic create or replacement up to 64 GiB.
- Supports startup filters for whole tool categories and individual tools. Disabled tools are omitted from the MCP schema and cannot be called through the server.
- Disabling `networking` hides tools tagged for networking, including selected tools whose primary category is elsewhere. It is a registration filter, not a network sandbox: explicitly re-enabled shell/PTY tools can inspect network data or make requests, filesystem tools can still read local network configuration, and other enabled tools may access configured networks.
- Detects Hyprland, Sway, Niri, GNOME, KDE Plasma, COSMIC, other graphical sessions, and headless sessions.
- Reports Linux distribution, kernel, architecture, init system, hostname, uptime, CPU count, load, memory, swap, processes, and mounted filesystem capacity.
- Reads bounded `/etc/fstab` entries, exposing mount targets, filesystem types, source classifications, allowlisted option flags, and dump/fsck fields while omitting exact source identifiers and arbitrary option values.
- Reads bounded `/etc/crypttab` entries, exposing mapper names, device/key-source classifications, explicit modes, selected flags, token/keyscript-presence metadata, and whether activation formats the mapping while omitting device identifiers, key paths, and option values.
- Reads system-wide Linux Pressure Stall Information (PSI) for CPU, memory, and I/O, including recent stall-time averages and cumulative stall microseconds. Kernel support varies; PSI averages describe time spent stalled and are not CPU-utilization percentages.
- Samples aggregate and per-logical-CPU utilization with memory, swap, load, and uptime over 2-20 bounded intervals; each request spans at most 60 seconds.
- Samples CPU time, resident/virtual memory, thread count, and storage-layer read/write counters and rates for up to 32 explicitly selected PIDs over bounded intervals, checking procfs start-time identity and omitting command lines, environments, and working directories. I/O counters may be unavailable under procfs permission rules.
- Samples cgroup-v2 CPU use/throttling, memory and swap use/limits, and PID counts/limits for up to 32 explicit PIDs. It checks each process's start time and cgroup membership around each sample and returns data only when the cgroup namespace and hierarchy root are safely visible.
- Groups namespace inode references by type across up to 5,000 stable process entries visible through procfs, with bounded reference counts and one representative PID. Child-namespace entries count future-child targets; results exclude process names and command lines and may be partial under procfs access restrictions.
- Reports scheduler policy and priority, CPU and memory-node affinity, cgroup membership, selected namespace IDs, and available no-new-privileges/seccomp/effective-capability fields for one explicit PID. When a cgroup-v2 hierarchy can be safely mapped in the same cgroup namespace, it also returns CPU, memory, swap, and PID limits plus cumulative counters for the process cgroup and up to 15 ancestors. The bounded snapshot checks process start time before and after collection and omits command lines, environments, and working directories.
- Lists Docker and Podman containers through standard local API sockets, with forced-local Podman CLI fallback, and inventories containerd/CRI-O containers through `crictl` over fixed local runtime sockets. Returns bounded ID/name/image/state metadata. Only Docker/Podman entries receive short-lived action tokens; CRI entries are read-only. Command arguments, environment, labels, mounts, logs, and remote endpoints are excluded.
- Lists local Docker/Podman image IDs and exact tags/digests through fixed local endpoints.
- Pulls one fully qualified Docker/Podman image reference, adds a tag to a local image, or removes one exact local tag after confirmation. Podman pulls may use credentials configured for the current server identity; Docker API pulls do not forward client credentials and may fail for private registries. Tag overwrite is refused after revalidation, though an external retag in the final read/action interval can race; forced removal is refused.
- Creates one stopped Docker/Podman container from an exact locally present image after explicit confirmation. It passes an optional command as an argument array and can attach existing named volumes, bind existing host files/directories read-only by default, publish loopback-default IPv4 ports, and set memory/CPU limits. Named-volume copy-up and implicit volume creation are disabled; an exact existing non-default local network can be selected, while privileged mode remains unavailable. The container is not started, and an image-declared VOLUME may still create an anonymous volume.
- Starts, stops, restarts, pauses, unpauses, or removes one listed Docker/Podman container after fresh identity validation and explicit MCP client confirmation. It uses current-user socket/OS permissions, never forces removal, and does not request volume deletion. A rootful engine socket can still perform host-privileged operations.
- Lists local QEMU/libvirt domains through fixed `qemu:///system` and `qemu:///session` connections, returning bounded UUID, name, state, active ID, and short-lived identity-token metadata. Remote URIs and domain XML/configuration are excluded.
- Starts, gracefully shuts down, reboots, suspends, or resumes one exact listed libvirt domain after fresh UUID-bound identity validation and explicit MCP client confirmation. It uses the current account's libvirt permissions, never force-powers-off or undefines a domain, and does not invoke `sudo` or register `virsh`'s terminal polkit agent. Host authorization policy still determines whether the operation is allowed. Starting a guest runs its configured workload and may access configured host resources.
- Lists bounded VM metadata from one explicit `qemu+ssh` endpoint ending in `/system` or `/session`; query options, fragments, passwords, other transports, and other drivers are refused. It uses the server account's default SSH keys and an owned `SSH_AUTH_SOCK` when present, disables SSH config and agent forwarding, requires a known host key, and does not prompt for passwords.
- Starts, gracefully shuts down, reboots, suspends, or resumes one exact remote VM only after explicit confirmation bound to the endpoint, UUID, name, and current state. Remote libvirt permissions apply; a system-scope guest can use privileged resources on its host.
- Lists bounded snapshot names and parents for one exact remote VM token, and confirms disk-only snapshot creation for shut-off guests, exact reversion, or leaf-only deletion. The tools revalidate the full inventory and selected metadata and verify the result.
- `attach_remote_virtual_machine_disk` adds one existing raw/qcow2 volume from an active persistent remote directory pool to an unused virtio slot in a shut-off remote VM. It checks all visible remote VM definitions for disk reuse and changes only persistent configuration; the guest may alter the volume when it next starts.
- `create_remote_virtual_machine` defines one stopped remote QEMU/libvirt VM with bounded memory/vCPU, a newly created sparse qcow2 disk in an active persistent directory pool, and an optional existing persistent network. It validates the generated XML and verifies the saved definition. It does not install an OS or start the VM; a partial failure may leave the new disk for inspection.
- `configure_remote_virtual_machine` changes memory/current-memory and vCPU values for one shut-off remote VM. Confirmation is bound to the full current definition and requested values; the saved configuration is validated and read back, and the guest is not started.
- `configure_virtual_machine` changes memory/current-memory and vCPU values for one shut-off local VM. Confirmation is bound to the full current definition and requested values; the saved configuration is validated and read back, and the guest is not started.
- Lists remote virtual networks and storage pools from one validated `qemu+ssh` endpoint. The storage inventory can include bounded volume names and size metadata for one exact returned pool; paths, volume keys, and XML are omitted. Starts/stops one exact network or pool, or changes its autostart, after endpoint, UUID, and current-state confirmation and post-action verification. Stopping a network disconnects its guests; stopping a pool can interrupt guest storage access. These tools require a trusted SSH host key and remote libvirt permissions.
- `create_virtual_machine` defines one stopped local QEMU/libvirt guest with bounded memory and vCPU values, a new sparse qcow2 disk in a persistent running directory pool, and an optional existing persistent network. The generated XML is validated and the resulting guest is rechecked. It does not install an operating system or start the guest; a partial failure may leave the new disk volume for inspection.
- `attach_virtual_machine_disk` attaches one existing raw/qcow2 volume to an unused `vdb`-`vdz` virtio slot in a shut-off VM's persistent configuration. It checks visible local VM definitions for disk reuse, updates configuration only, and verifies the saved result without formatting the volume or starting the VM.
- Lists up to 512 snapshot names for one exact local VM using its short-lived identity token. The local tool excludes remote connections and snapshot XML; remote inventory is available through the separate remote snapshot tools.
- Creates a disk snapshot only for a shut-off VM, reverts to one exact snapshot, or deletes one exact leaf snapshot after explicit confirmation. Reversion may discard later guest changes and resume saved running state; deletion refuses snapshots with children. The full bounded snapshot inventory and selected snapshot metadata are rechecked.
- Lists bounded local libvirt virtual networks with active, persistent, and autostart state through fixed read-only QEMU system/session connections. Network XML, bridges, addresses, DHCP leases, and network ports are omitted.
- `create_libvirt_isolated_network` retains the simple isolated-network flow. `create_libvirt_network` can also define inactive IPv4 NAT or routed networks with an optional bounded DHCP range, or a direct network on an existing Linux bridge. NAT/routed subnets are checked against current host routes and addresses; bridge mode exposes guests to the bridge LAN. Starting is a separate confirmed action. `configure_libvirt_network_ipv4` can update the address and DHCP range of an existing persistent inactive NAT/routed network while preserving its mode, UUID, bridge, and autostart state; it refuses active networks and unsupported XML. IPv6, Open vSwitch, host-bridge creation, and arbitrary XML remain unsupported.
- Lists bounded local libvirt storage pools with state and human-readable capacity summaries. An exact pool name plus system or session scope can request bounded volume names, types, capacities, and allocations; filesystem paths, volume keys, and pool XML are omitted.
- Starts or stops one exact local libvirt virtual network or storage pool, or changes its persistent autostart setting, after exact client confirmation. UUID, scope, and current state are revalidated; network stop is immediate, and stopping a pool may interrupt guest storage access. Pool definitions and existing volume contents are not changed.
- Creates one new sparse raw or qcow2 volume from 1 MiB through 1 TiB after exact confirmation in a persistent, running, directory-backed libvirt pool. The tool rechecks pool UUID/state and that the requested name is unused, then verifies the created volume's name, capacity, and format. Guest writes can overcommit pool storage; the volume is not attached to a VM.
- Lists bounded kernel rfkill devices such as WLAN, Bluetooth, WWAN, NFC, UWB, GPS, and FM radios, exposing only index, driver name, type, and soft/hard blocked state.
- Soft-blocks or unblocks one exact rfkill device after fresh identity validation and explicit MCP client confirmation. Hard blocks cannot be overridden. Blocking can interrupt network access and this MCP client; unblocking does not connect to a network, though a network manager may react.
- `list_bluetooth_devices` lists only devices already cached by BlueZ; it does not scan. Device names and addresses can identify nearby or previously used devices. `manage_bluetooth_pairing` pairs one exact unpaired cached device after confirmation and state revalidation. BlueZ pairing initiates a connection and may invoke an authentication agent; bluetoothctl may also mark the device trusted depending on BlueZ version.
- Lists logical CPU online state, topology, model/vendor, and available frequency readings as a bounded snapshot.
- Lists bounded NUMA node online state, CPU membership, per-node total/free memory, and distances to online nodes from fixed sysfs attributes. Kernel and architecture differences may leave individual fields unavailable; the tool exposes no topology controls.
- Lists bounded DRM GPU card identifiers and driver metadata. It reports AMDGPU busy-percent/VRAM, Intel i915/Xe temperature and cumulative energy where exposed, actual Xe per-GT frequency, Nouveau temperature, and optional NVIDIA utilization, memory, temperature, and power through a fixed `nvidia-smi` query. Intel and Nouveau utilization/memory remain unavailable unless the driver exposes a supported interface. Separate controls handle standard hwmon power caps where available and documented Intel Xe per-GT maximum-frequency ceilings; other vendor-specific GPU settings, process lists, UUIDs, and serial-number fields are not queried.
- Inspects metadata and lists directories for explicit absolute paths, and reads bounded UTF-8 text from regular files with current OS permissions.
- Creates a new UTF-8 text file at one exact absolute path after client confirmation. Content is capped at 64 KiB, existing targets are never overwritten, mode is 0600, and paths under `/proc`, `/sys`, `/dev`, and `/run` are excluded.
- Replaces the full content of one existing regular UTF-8 text file up to 64 KiB after confirmation bound to its current and replacement digests. It refuses multiply linked, setuid/setgid, and files with visible capability/IMA/EVM security attributes; writes in place to preserve owner, mode, ACL, and checked xattrs; verifies the result; and attempts to restore the original content after a write failure. Modification/change times update.
- Reads binary files in pages up to 1 MiB and creates, atomically replaces, or appends strict-base64 payloads up to 4 MiB per confirmed call. Appending supports larger files over multiple calls; replacement preserves owner, mode, ACL, and visible xattrs.
- Deletes one regular binary or large file after confirmation bound to its canonical path, parent directory, and current file identity. This unlinks the path; it is not secure erasure.
- Creates missing directory components or recursively deletes one exact directory tree after confirmation. Deletion is capped at 20,000 entries and never follows symlinks.
- `list_directory` returns bounded metadata for immediate directory entries or, with `recursive=true`, descendants using relative paths. Recursive scans stop at 5,000 entries or 128 levels and never descend through symlinks.
- `manage_directory_tree` copies one tree to a new destination with atomic no-overwrite publication, or moves it by same-filesystem rename. It is capped at 20,000 entries, 64 GiB of regular-file data, and 256 levels; copy checks currently available destination bytes against the source's logical file size and (when reported) free inodes against up to one inode per entry plus the destination root, during confirmation and again before staging. Internal hard links reduce inode use; filesystem allocation and concurrent writes can still cause a later no-space failure. It copies regular files, directories, symlink targets, rwx modes, modification times, and hard-link relationships within the copied tree, while refusing special files and nested mount points. Copies do not preserve owners, ACLs, xattrs, or access times. Move preserves existing metadata and refuses mounted trees; both actions bind the source tree and destination parent to confirmation.
- Creates/removes symlinks and changes numeric UID/GID ownership on one exact regular file or directory; `recursive=true` changes a bounded directory tree of at most 20,000 entries and 256 levels, requires the MCP server to already run as root, does not follow symlinks, and refuses special files or mounted paths. A partial recursive failure leaves earlier changes in place, chown may clear setuid/setgid bits, and hard-linked entries can affect aliases outside the tree. General xattrs and Linux POSIX access/default ACLs can also be set or removed after confirmation.
- Changes standard owner/group/other rwx bits for one exact regular file or directory after confirmation bound to its canonical path and old/new octal modes. The change is nonrecursive, never sets special bits, uses current OS permissions, and may update mode-corresponding POSIX ACL entries and effective permissions.
- Lists bounded block-device capacity, partition status, removable/read-only flags, rotational status, and logical block sizes from sysfs, without serial numbers or storage actions.
- Maps active block-device component and holder relationships from sysfs, classifies device-mapper crypt/LVM/multipath and MD RAID layers, and reports MD level/member/degraded counts, current sync action, completed/total sync sectors, and mismatch sectors when exposed. The kernel mismatch count is sectors rewritten or that would have been rewritten, not distinct corrupt blocks. Device-mapper UUIDs, serials, and loop backing-file paths are omitted; relationships are a non-atomic snapshot.
- Reads bounded LVM2 volume-group extents and logical-volume layout, pool/origin relationships, and available data/metadata percentages through fixed read-only `vgs`/`lvs` reports. Physical-volume paths and UUIDs are omitted; active/in-use state is unavailable in LVM read-only mode.
- Creates or grows one exact LVM logical volume, creates/removes one snapshot, or restores one exact classic copy-on-write snapshot into its named origin after confirmation. Restore merges the snapshot and deletes that snapshot LV, overwriting origin changes made after the snapshot; it requires the server to already run as root, `lvconvert`, `dmsetup`, and `fuser`, and both LVs to be active but closed, unmounted, not swap, and free of unrelated holders. The classic snapshot must be healthy with a known COW data percentage below 100%; thin-snapshot restore is not supported. The tool rechecks volume-group capacity, snapshot/origin relationship, LV inventory, the snapshot COW percentage, device identities, open counts, and use state after confirmation; growth does not resize the filesystem inside the LV. The resulting LV topology is checked, but block contents are not independently read back.
- Lists local and received Btrfs snapshots beneath an explicit mounted top-level subvolume (ID 5). After exact confirmation, creates a read-write or read-only snapshot at a new path, deletes one exact snapshot, or restores a read-only snapshot as a writable clone at one exact unmounted, non-default subvolume. Restore requires a new sibling backup path for the old target. It atomically exchanges the writable clone with the target, then moves the original from staging to the backup path without overwriting; if interrupted between those steps, the original can remain at staging while the clone occupies the target. It does not change /etc/fstab or the default subvolume. Restore refuses nested subvolumes, ordinary subvolume sources, and targets that are mounted or default. Create/delete also refuse ordinary subvolumes, mounted snapshots, and nested subvolumes. Snapshots share copy-on-write extents and are not independent backups; nested subvolumes are not recursively included.
- Mounts or unmounts one exact existing `/etc/fstab` target after explicit confirmation. It uses configured source/options in the current mount namespace, refuses root/pseudo/swap/symlinked/writable-path/stacked targets, does not recurse or force/lazily unmount, and does not invoke sudo, polkit, or interactive elevation; util-linux and fstab rules determine authorization.
- Reads bounded cumulative per-device read/write/discard/flush counters from sysfs; sectors use 512-byte units, results are snapshots rather than rates, and layered devices may account for activity at multiple layers.
- Reads an on-demand SMART health snapshot for one exact whole-device name using optional `smartctl`; it returns selected health/temperature/lifetime fields and bounded ATA attributes without serials. It starts no self-test and changes no device settings; ATA/SCSI drives reported in standby are skipped, while other protocols may leave low-power state.
- Reads bounded temperature, fan-speed, voltage, current, power, energy, and humidity inputs from hwmon and thermal-zone sysfs. Values include raw readings and normalized units where standardized; hwmon temperature exceptions and humidity readings are flagged as driver-defined. Thresholds, alarms, and controls are excluded.
- Lists bounded display backlight devices and their configured/maximum brightness. After exact client confirmation, changes one exact device to a value within its reported range, rechecks state and device identity, and verifies the configured value; hardware-reported brightness can differ, and zero can turn off the panel backlight.
- Lists bounded PCI and USB vendor/product IDs, class codes, and driver names from sysfs without serial numbers or device labels.
- Reports selected SMBIOS/DMI system, board, chassis, and BIOS vendor/model/version/date fields from `/sys/class/dmi/id` where available. Serial numbers, UUIDs, asset tags, modaliases, and raw DMI tables are not read.
- Lists TPM class devices with kernel-reported specification version and optional bound-driver name; it issues no TPM commands and does not read command-backed status, PCR values, or endorsement keys.
- Reads bounded pages from the kernel-exported TPM firmware event log, parsing legacy SHA-1 and crypto-agile TPM 2.0 records with short event-data previews; it does not issue TPM commands, read PCR values, or validate attestation.
- `create_tpm_attestation` requests a TPM 2.0 quote for selected SHA-256 PCRs from an existing persistent key after confirmation. It binds a caller-supplied 32-byte nonce, returns bounded quote/signature/PCR/public-key artifacts, and locally verifies the signature and included PCR values. A remote verifier must still trust the attestation key and judge the measurements; quote data can reveal measured boot/software state.
- Lists a broader bounded udev device inventory with kernel paths/names, subsystem/type, attached drivers, device-node major/minor numbers, and numeric vendor/product IDs. Serial properties, human-readable labels, device-node symlinks, and arbitrary udev properties are omitted.
- Lists kernel ALSA sound cards and playback/capture PCM endpoints from bounded procfs snapshots.
- Lists current-session userspace audio sinks and sources, default endpoints, and available mute/volume metadata through `pactl` or `wpctl`; endpoints may include network audio tunnels, while active application streams and audio content are excluded.
- Changes the volume, mute state, or default status of one exact current-session sink/source after explicit client confirmation. The endpoint may be a network audio tunnel. Volume is limited to 0–100%, endpoint identity and state are rechecked before the command, and the result is verified; volume and mute changes affect all clients using that endpoint.
- Lists bounded power-supply type/status, capacity, charge/energy, voltage/current/power, temperature, and cycle-count snapshots from sysfs without reading manufacturer, model, serial-number, or writable charge-control attributes.
- Reports kernel-exported suspend/hibernate choices and selected memory/hibernation modes from fixed `/sys/power` attributes. It does not request a transition or infer firmware/swap readiness.
- Lists active system logind inhibitors with owner, UID/PID, affected operations, reason, and mode. Command lines and derived process names are excluded.
- Queries logind's current availability/authorization result for a selected power operation, including firmware-setup reboot where supported; this does not guarantee hardware or firmware transition success.
- Requests poweroff, reboot, halt, suspend, hibernate, hybrid sleep, suspend-then-hibernate, or firmware-setup reboot only after explicit client confirmation. Logind actions use fixed methods with non-interactive authorization; firmware-setup reboot uses a fixed `systemctl` request. Inhibitors are not bypassed, no privilege elevation is requested, and transition completion is not verified.
- Reads the active and available power-profiles-daemon profiles through `powerprofilesctl`. `manage_power_profile` switches to one available `power-saver`, `balanced`, or `performance` profile only after state-bound client confirmation, rechecks the profile set, and verifies the result. The daemon stores the selected profile for startup restoration; actual hardware behavior depends on drivers and firmware. Both tools require `powerprofilesctl` and appear only while the `power` and `hardware` categories are enabled.
- Reads machine-readable systemd timedated timezone, RTC-local, network-time support/enabled/synchronized, system-time, and RTC-time fields, plus a bounded list of host timezone identifiers. After exact client confirmation, changes one timezone or toggles network time synchronization; it does not directly set the system clock or change RTC mode; network synchronization may adjust the clock after NTP is enabled.
- Reads bounded chrony tracking fields and current source rows, plus selected systemd-timesyncd active-server and configured-server properties when the corresponding clients are installed. The query is read-only, works with chrony on non-systemd Linux hosts, and may return source hostnames, IP addresses, and timing metrics.
- Lists configured CUPS printer queues, enabled/printing state, job-acceptance state, and default destination through bounded `lpstat` output. After exact client confirmation, `manage_printer` can enable/disable one queue or accept/reject new job submissions; it revalidates and verifies queue state. Enabling may resume queued documents, and no action cancels queued jobs. Job lists, users, document titles, printer device URIs, and unconfigured network devices are not inspected.
- Lists bounded loaded kernel-module names, sizes, reference counts, and states without module addresses or dependency strings.
- `manage_kernel_module_startup` adds or removes one generated `/etc/modules-load.d` entry for an exact module installed for the running kernel. It refuses to shadow a same-named config or duplicate an exact module entry in standard configuration directories. The change affects future systemd-managed boots only; enabling does not load the live module, and disabling does not unload it. `list_kernel_parameters` reads a fixed allowlist of four runtime sysctls (`vm.swappiness`, `vm.vfs_cache_pressure`, `fs.inotify.max_user_instances`, and `fs.inotify.max_user_watches`) and returns short-lived state-bound tokens and product-allowed value ranges. `manage_kernel_parameter` changes one exact value after confirmation, rechecks its observed value and procfs identity, and verifies the result. Its confirmation warns that `vm.vfs_cache_pressure=0` can prevent dentry/inode reclaim under memory pressure and cause out-of-memory conditions. `manage_persistent_kernel_parameter` creates, updates, or removes one generated `/etc/sysctl.d` file for the same four keys on systemd hosts. It checks bounded standard sysctl.d files for exact/wildcard conflicts, confirms the exact file state, and does not apply changes to the running kernel. Its prompt describes value-specific risks: zero `vfs_cache_pressure` can cause out-of-memory conditions, higher cache pressure can reduce performance, zero swappiness delays swap until a zone's high watermark, and higher inotify watch limits can permit more kernel memory use. Other boot services may later change the effective runtime value. Both sysctl tools use current OS permissions without privilege elevation; the runtime write has a narrow race with concurrent external writers. `manage_kernel_command_line` adds or removes one simple argument across current boot entries reported by a root-owned `grubby`. When grubby is unavailable, it supports a bounded static `GRUB_CMDLINE_LINUX` or `GRUB_CMDLINE_LINUX_DEFAULT` assignment in `/etc/default/grub` plus direct regeneration of exactly one standard `/boot/grub/grub.cfg` or `/boot/grub2/grub.cfg` target. It refuses `root=` and unsupported shell/config layouts, binds confirmation to the complete boot/config/generator state, checks that generated entries changed only by the requested argument, and restores the defaults file if generation fails; if a rollback cannot complete, the response names any retained recovery copy. The fallback runs `grub-mkconfig`, including its root-owned `/etc/grub.d` hooks, with current OS permissions and no privilege elevation. Boot arguments can prevent startup or alter security and device behavior; future-entry templates on grubby hosts remain separate. `manage_initramfs_rebuild` rebuilds the exact standard image for the running kernel through `dracut`, `update-initramfs`, or a simple literal `mkinitcpio` preset, only when one safe manager/target pair can be identified. It confirms the image and generator state, uses current OS permissions, and warns that configured generator modules, config scripts, and post-update hooks may run. Shell-based presets, extra default options, UKI output, and nonstandard targets are refused.
- Reads active Linux security-module names, kernel lockdown mode, SELinux enforcement, maximum supported policy-format version, MLS and unknown-handling state, exposed policy capabilities, UEFI `SecureBoot` and `SetupMode` variables where exposed, and a fixed allowlist of kernel security sysctls. The reported SELinux version is the kernel's maximum supported format, not the loaded policy's version. Firmware variables are bounded raw snapshots; missing or malformed values remain unavailable rather than being treated as disabled. The tool does not verify the full boot chain, infer compliance, or change settings.
- Lists bounded pages of loaded AppArmor profile names and kernel-reported modes from securityfs. It does not return profile rules or assess policy completeness.
- After exact client confirmation, `manage_apparmor_profile` changes one exact loaded profile between enforce and complain mode using the installed `aa-enforce` or `aa-complain` utility's `--profile` option. It updates the matching local policy file and reloads it; complain mode generally allows ungranted accesses and logs them, while explicit deny rules remain enforced. Enforce mode may interrupt a confined application. Unconfined and other modes are refused, and the tool does not invoke sudo.
- Lists bounded current and pending SELinux boolean values from the fixed selinuxfs boolean directory. Supports substring filtering and index-based paging.
- After exact client confirmation, `manage_selinux_boolean` enables or disables one listed boolean at runtime or persistently across reboots. Persistent updates use `setsebool -P`, may rebuild policy, and depend on host authorization.
- After exact client confirmation, `manage_selinux_context` restores the policy-defined SELinux type for one existing regular file or directory. It uses nonrecursive `restorecon` without force-reset options, preserves customizable labels and user/role/range fields, and verifies the resulting type.
- `manage_selinux_fcontext_rule` adds or removes one persistent local SELinux file-context rule for an exact existing path. It creates an anchored literal expression limited to the path and its current file type, requires an already-root server, binds the local-rule inventory and `semanage` identity to confirmation, and verifies the result. It does not relabel the current object or recurse; use `manage_selinux_context` separately to apply an added rule.
- Reads bounded pages from the ASCII IMA runtime-measurement log, with the kernel's measurement-count and violation counters where exposed. Page offsets are byte offsets returned by the tool; record and scan limits are enforced. Template data can include measured file paths, signatures, or event payloads. The tool opens the fixed securityfs interfaces read-only and does not stage/delete measurements or read or verify TPM PCR values.
- Reads bounded pages of raw active IMA policy rules when the kernel exposes policy readback. The fixed securityfs policy file may require `CONFIG_IMA_READ_POLICY` and `CAP_SYS_ADMIN`; rule text may include filesystem identifiers or security labels. The tool opens it read-only and makes no policy changes.
- Lists installed system packages from dpkg, RPM, pacman, or APK metadata without refreshing repositories or changing installed software.
- Creates managed current-user Python virtual environments and lists installed project names and versions from bounded distribution metadata without running environment code. Exact pip install, upgrade, and uninstall actions require confirmation; package builds may run code as the current non-root user and may access the public package index.
- Installs, upgrades, or removes one exact system package, or requests upgrades for all eligible installed system packages, after explicit client confirmation. Uses the current account's OS permissions without elevation; package scripts and dependency changes can affect other software and services. Pacman install/upgrade also performs a full system upgrade.
- Lists Flatpak refs in the default system, configured named system installations, and the current-user installation, installed system Snaps, and the current user's default Nix profile. ## Safety and scope

- `read_binary_file` returns base64 pages of up to 1 MiB. `write_binary_file` handles up to 4 MiB per confirmed call; repeated append calls support larger files. For larger atomic creates/replacements, `begin_binary_file_upload` confirms the exact target, total size, and SHA-256, then creates a private staging file. `append_binary_file_upload` accepts sequential chunks of up to 4 MiB, and `commit_binary_file_upload` publishes only after checking the complete size and digest; `abort_binary_file_upload` discards the stage. Each upload is capped at 64 GiB and the server reserves at most 128 GiB across active uploads. Begin checks available destination-filesystem space against active reservations. Uploads expire after one hour of inactivity, and hidden mode-0600 staging files are removed within 30 seconds after expiry. Graceful server shutdown removes active stages; an unexpected process exit can leave a hidden staging file. Replacement preserves owner, mode, ACL, and visible xattrs, and refuses visible file-capability, IMA, or EVM attributes. Paths under `/proc`, `/sys`, `/dev`, and `/run` are excluded.
- `run_shell_command` runs arbitrary shell code, so it can perform any operation allowed to its selected execution identity. Every call needs explicit MCP client confirmation and a typed phrase bound to the command, working directory, stdin, environment overrides, timeout, output cap, and identity. Command and stdin are capped at 64 KiB; overrides at 64 entries/64 KiB; runtime at 30 minutes and combined output at 1 MiB. It runs as the server account by default; `run_as="root"` uses `sudo -n` and works only when sudo policy permits noninteractive execution, or runs directly when the MCP server is already root. It does not bypass Linux permissions, namespaces, capabilities, SELinux/AppArmor, or sudo policy. Execution has no TTY, and process-group cleanup cannot stop processes that detach or create new sessions.
- `start_terminal_session` provides an interactive PTY after exact-request confirmation. Every `write_terminal_session` call confirms the exact text and optional resize before sending it; a newline or control character can execute commands. Reads are non-mutating. Sessions last at most 30 minutes, retain at most 1 MiB output, and allow up to 8 concurrent processes. Detached processes may outlive close or timeout cleanup. `run_as="root"` and root-launched server operation require host sudo policy or an already-root process.
- `list_storage_topology` reads bounded names and attributes from `/sys/class/block`, including `slaves` and `holders` links plus MD and device-mapper metadata. It classifies device-mapper UUID prefixes but never returns UUIDs, serials, or loop backing paths. The graph can change during collection; per-node identity checks detect some races, and result/edge caps can leave partial relationships.
- `list_lvm_inventory` uses fixed-field `vgs` and `lvs` JSON reports with `--readonly`, bounded time/output/row/result limits, and no caller-supplied command fragments. It returns volume-group size/free capacity and extent counts plus logical-volume size/layout, pool/origin names, and available data/metadata percentages. Physical-volume paths and UUIDs are omitted. LVM `--readonly` reads metadata without locks or device-mapper communication, so active/in-use state is not reported; normal `lvs` reporting also omits hidden internal volumes.
- `manage_lvm_volume_group` creates a new group (`action="create"`, the default), adds blank PVs to an existing group (`action="add_pv"`), removes exact unused PVs (`action="remove_pv"`), or moves all allocated extents between two exact PVs (`action="move_pv"`, with `physical_device_paths=[source, destination]`). Creation and extension initialize blank devices and write LVM metadata, which can make existing data inaccessible. PV removal is limited to devices with zero allocated extents; it leaves the LVM label in place. Move extents first with `pvmove --atomic`; the destination must have at least twice the source allocation free, and the operation is bounded to 30 minutes. Active logical volumes may use the PVs while migration runs. Keep both devices in place and inspect LVM state if the command times out or is interrupted. Recognized signatures on new PVs, mounted/swap devices, active holders, whole disks with partitions, and duplicate device identities are refused. New-group creation uses at most one PV per physical disk; existing groups may contain multiple PVs from one disk. Exact group/PV membership, allocated extents, and block-device identities are re-read after confirmation, then resulting group membership is verified. Actions use current-user permissions without elevation.
- `manage_lvm_volume` creates and grows LVs, creates/removes snapshots, restores one exact classic COW snapshot into its named origin, and shrinks only linear raw or verified ext4 LVs. Snapshot restore merges the snapshot into the origin and removes the snapshot LV, so origin changes made after the snapshot are lost; it requires the server to already run as root, `lvconvert`, `dmsetup`, and `fuser`, and both devices to be unmounted, not swap, closed, and free of unrelated holders. Thin snapshots and active snapshot merges are refused; if another process opens a device after the final check, LVM may defer the merge, and the tool reports if the snapshot remains. The post-action check verifies the origin and snapshot LV topology and size, not the block contents. Shrinking requires an unmounted volume, effective root for holder checks, and a fresh `fuser` check for open block-device users. For ext4, `lvreduce --resizefs` shrinks the filesystem first and refuses to reduce the LV if filesystem shrinking fails; raw LV shrink can discard data in the removed tail. XFS, other filesystem signatures, snapshots, thin/striped/RAID layouts, mounted/swap/held volumes, and unsupported dependencies are refused for the shrink action. The command targets a VG extent count and revalidates LVM, filesystem, and active-use state after confirmation. LVM grow does not resize the filesystem.
- `manage_luks_mapping` formats a verified blank device as LUKS1/LUKS2, opens/closes/grows one exact mapping, adds a key from a separate private key file, or removes one exact active keyslot after state-bound confirmation. It refuses a full keyslot table, removal of the last active slot, and removal of a LUKS2 slot referenced by a token; token-to-slot bindings are included in state revalidation. Use `list_luks_tokens` for redacted LUKS2 token inventory and `manage_luks_token` for confirmed token removal, keyslot unassignment, JSON import into an unused ID, or private-file JSON export. Full LUKS reencryption and conversion are unsupported. Header backup and restore are available through `manage_luks_header`. Formatting refuses recognized signatures, mounted/swap devices, holders, backing-device relations, and whole devices with child partitions. Existing/new key files must be private, server-owned regular files; the existing key goes through stdin and the new key through an anonymous in-memory file descriptor, never argv or the confirmation prompt. Close is never forced, and resize changes only mapped block size. Commands use current OS permissions without sudo.
- `list_luks_tokens` reports only LUKS2 token IDs, escaped and bounded type labels, keyslot bindings, and active keyslot IDs for one exact block device; token JSON payloads and provider-specific fields are omitted. `manage_luks_token` removes one exact token of any type or unassigns one exact token-to-keyslot binding after client confirmation bound to the complete bounded header metadata and cryptsetup executable identity. It verifies the exact metadata change and unchanged keyslots. JSON import reads a server-owned, single-link mode-0600 file up to 4 MiB and never replaces an occupied token ID; JSON export atomically publishes a new no-overwrite mode-0600 file and never returns token JSON to the client; an unexpected server exit can leave its hidden mode-0600 staging file. Import/export files can contain provider-specific authentication data; external-token plugin loading is disabled for token actions. Removing a token can disable token-based unlocking; unassigning the final binding leaves the token present but unusable through a keyslot. Native keyring-token enrollment and full LUKS reencryption/conversion remain unsupported. Commands use current OS permissions without sudo or interactive elevation. See the upstream [`cryptsetup-token(8)`](https://man7.org/linux/man-pages/man8/cryptsetup-token.8.html) manual.
- `manage_luks_header` creates a private, no-overwrite backup of the LUKS header and keyslot area, or restores one exact private backup after confirmation. It binds the block-device identity, LUKS UUID/version, keyslot/token state, backup-file identity, and SHA-256 digest; refuses restore on mounted/swap, held, read-only, or partitioned whole devices; and verifies the restored UUID, keyslot/token state, and unchanged backup. Restore replaces every current keyslot and LUKS2 token record. A backup plus a passphrase valid when it was made can unlock the encrypted data even after that passphrase is later changed or removed, so protect and securely erase backups; overwriting the encrypted data area may also be needed for secure erasure. When the target has no recognized current LUKS header, restore requires `expected_luks_uuid` from a trusted prior inventory. Cryptsetup checks header compatibility before restoring. See the upstream [`luksHeaderBackup(8)`](https://man7.org/linux/man-pages/man8/cryptsetup-luksHeaderBackup.8.html) and [`luksHeaderRestore(8)`](https://man7.org/linux/man-pages/man8/cryptsetup-luksHeaderRestore.8.html) manuals.
- `manage_ext4_filesystem` creates ext4 only on a verified blank, unused block device, grows an existing ext4 filesystem to use additional device capacity, or shrinks an unmounted ext4 filesystem to an exact `target_size_bytes`. Shrinking refuses mounted, swap, or held devices and requires read-only `e2fsck -f -n` checks to report clean before and after; it never repairs errors or changes the backing block device, partition, or LVM volume, and `resize2fs` may reject a target that is too small. Creation refuses recognized signatures, active mount/swap use, holders, and whole devices with child partitions. Filesystem and device state are rechecked; no sudo or interactive elevation is used.
- `manage_xfs_filesystem` creates a basic XFS filesystem on a device with no recognized signatures or grows a mounted XFS filesystem without a real-time section to the available device size. Growth requires exactly one writable current-namespace mountpoint, and XFS cannot be shrunk. Raw data may still be present; creation does not force mkfs over signatures. Device identity and filesystem geometry are rechecked.
- `manage_btrfs_filesystem` creates a single-device Btrfs filesystem on one verified unused block device, grows one mounted filesystem after backing-device expansion, or shrinks one mounted filesystem to an explicit byte size. Shrinking requires the server to already run as root; the tool checks Btrfs's current minimum device size and sector alignment, binds both to confirmation, then rechecks before acting. Shrinking can relocate data and cause heavy I/O; concurrent writes or active swapfile extents in the target region can make it fail. It resizes only the filesystem layer, so any partition, LVM, LUKS, or backing-device reduction must happen separately after verifying the filesystem shrink. Creation refuses recognized signatures, mounted/swap devices, holders, and whole devices with child partitions; it never forces formatting, although arbitrary raw data can still be present. Multi-device filesystems remain outside this tool.
- `manage_md_raid` creates Linux MD RAID0/1/4/5/6/10 arrays, assembles one exact complete, clean, non-degraded native version-1 array in read-only mode by default (with an explicit read-write option), adds/removes spares, replaces a healthy member, marks/removes faulty members, starts check-only consistency scrubs, or stops one exact idle read-write array when unused. Assembly binds the UUID, metadata generation, geometry, roles, component UUIDs, and block-device identities; it refuses dirty/stale or incomplete metadata, spares, reshape/recovery metadata, and legacy/external metadata, and does not scan, force, or start degraded arrays. Read-only assembly starts no resync/recovery/reshape writes; read-write assembly can update MD metadata, and subsequent filesystem/application writes can modify member data. A stopped array remains unavailable until assembled again. Checks run in the background, record rather than repair mismatches, and read errors can still trigger ordinary MD recovery writes. RAID4 uses a dedicated parity member; failure marking may reduce redundancy, replacement recovery leaves the old member in service, and RAID4/5 require at least three members while RAID6 requires at least four. Creation refuses recognized signatures, mounted/swap devices, holders, read-only devices, whole disks with partitions, and multiple members on the same physical disk. Reshape, repairing scrubs, and boot-time assembly configuration remain unavailable; array/member state is revalidated and current-user permissions are used without sudo.
- `list_btrfs_snapshots` lists bounded local and received snapshots under one explicit mounted Btrfs top-level subvolume (ID 5), including UUID lineage, generation, and read-only state. `manage_btrfs_snapshot` confirms read-write/read-only snapshot creation, exact local/received snapshot deletion, or a constrained restore from a read-only snapshot. Restore stages a writable clone, atomically exchanges it with the exact unmounted non-default target so the target path stays occupied, then moves the original from staging to a new sibling backup path without overwriting. If interrupted between those steps, the original can remain at staging while the clone occupies the target; recovery paths are reported on failure. It preserves the old target and snapshot, refuses nested subvolumes, and does not change /etc/fstab or the Btrfs default subvolume. This does not switch the default subvolume or provide a system-root rollback. Create/delete refuse ordinary subvolumes, the default, mounted snapshots, and snapshots containing nested subvolumes; deletion commits the metadata transaction while block cleanup remains asynchronous. Snapshot creation can flush dirty data, snapshots are not independent backups, and nested subvolumes are not recursively captured. The tools use current OS permissions and do not invoke sudo.
- `manage_kernel_module` loads one installed module with `modprobe --ignore-install` or unloads one exact live module with `rmmod` after confirmation. It refuses built-in modules and modules with reported references or dependent holders. Loading may also load dependencies; these actions affect runtime state only and do not configure startup.
- `manage_kernel_module_startup` adds/removes one generated systemd modules-load.d file for the exact installed module. It scans bounded standard config directories and refuses duplicate module entries or same-name file overrides. It affects future boots only; it neither loads nor unloads the current module.
- `manage_local_identity` operates only on local identities through shadow-utils after confirmation and does not query NSS. It can create/delete users and groups, optionally remove a safe existing home during user deletion, lock or unlock an existing local password, set a listed shell, add/remove secondary-group membership, and relocate an existing home directory. Group membership may grant privileges defined by host policy, including sudo-equivalent access through an administrative group. Unlocking requires a usable local password hash. New users need an existing primary group, default to nologin, and start password-locked. The optional `create_home` flag creates the exact effective `useradd -D` home path from `/etc/skel` after confirmation; the destination must not exist, the base path must be root-owned and non-writable by group/other, and the bounded skeleton tree is re-read before execution. `action="move_home"` relocates one existing user-owned home to a new destination beneath `/home` or `/var/home`; it refuses nested mounts, unsafe path components, and an existing destination, and `usermod` refuses users with active processes. Cross-filesystem moves may need extra space and manual ACL/xattr ownership adjustment; a concurrent path/tree change can race after the final recheck, and a failed or interrupted move can leave partial state, so inspect both paths and account state before retrying. User deletion leaves home files in place by default. For `action="delete_user"`, the confirmed `remove_home=true` option removes only a real user-owned home beneath /home or /var/home; it binds tree metadata capped at 20,000 entries and 256 directory levels plus the parent identity, refuses mounted trees, and revalidates after `userdel` succeeds. It does not securely erase files or remove the mail spool. A failure after account deletion can leave the home tree partly or wholly present, so inspect the path before retrying. The operation uses no force mode, and host `USERGROUPS_ENAB` may remove an empty same-name private group. Configured `USERDEL_CMD` and shadow-utils lifecycle hooks make affected operations unavailable. Password and public SSH key changes use the separate confirmed `set_local_user_password` and `manage_local_ssh_key` tools. `list_sssd_domains` inventories simple standalone SSSD domain configuration; `manage_sssd_domain` toggles one existing configured domain with `sssctl` validation and exact state confirmation. Direct PAM stack editing and PAM managers outside Debian-style `pam-auth-update`, SSSD `conf.d` snippets, provider settings, and SSSD domain creation or broader edits remain unsupported.
- `list_pam_profiles` reads bounded package-supplied profiles from `/usr/share/pam-configs` and reports their debconf selection state, default flag, priority, and stack types without exposing profile contents or module arguments. `manage_pam_profile` changes one exact profile through `pam-auth-update` after confirmation bound to the profile catalogue, selection state, common PAM files, and utility identities. It requires the server to already run as root, never uses `--force`, does not validate authentication end to end, and may prevent SSH, sudo, console, or desktop logins. Keep the current session open and verify a separate login. Local edits to `common-*` may remain effective even when debconf selection changes.
- `manage_mount` accepts only one exact, unique valid `/etc/fstab` mount target whose directory already exists without symlink components. It refuses root, pseudo-filesystems, swap, targets beneath `/proc`, `/sys`, or `/dev`, and paths through unsafe writable directories; it uses fixed `mount --target` or exact `umount` arguments, refuses stacked mounts, and never uses recursive, lazy, or forced unmount options. Current mount state is checked before confirmation and after the command. The configured source/options remain hidden, but type-specific helper programs may run. The server does not invoke sudo, polkit, or interactive elevation; util-linux and fstab rules determine authorization.
- `list_fstab_entries` opens only `/etc/fstab` without following a final symlink, caps reads at 512 KiB and scans at 10,000 lines, and never returns raw source identifiers or arbitrary option values. Mount targets may reveal configured paths; only exact option tokens from a fixed allowlist are returned.
- `list_crypttab_entries` opens only `/etc/crypttab` without following a final symlink, caps reads at 512 KiB and scans at 10,000 lines, and omits encrypted-device identifiers, key paths, and arbitrary option values. Mapper names and boolean presence of hardware-token or keyscript options remain visible; the `swap` and `tmp` flags indicate formatting on activation and can erase existing mapped-device contents. It does not read key material or unlock devices.
- `get_pressure_stall_info` reads only fixed `/proc/pressure/{cpu,memory,io}` files. It creates no PSI triggers and reports each unsupported or malformed resource as partial/unavailable.
- `list_namespace_inventory` scans at most 5,000 numeric PID entries visible through the current procfs mount, validates process start time around namespace-link reads, and caps results at 256 inodes per namespace type. Namespace reference counts are non-atomic and can omit hidden or inaccessible processes; `pid_for_children` and `time_for_children` count links to future-child namespaces rather than current membership.
- `list_network_manager_profiles` requests only UUID, name, type, attached device, and autoconnect fields from `nmcli`; it does not request secret values or change connection profiles.
- `get_network_manager_profile_dns` reads selected saved DNS properties for one exact UUID using a fixed `nmcli connection show` field list. It does not request active connection data or secret properties and does not change the profile; DNS server addresses and search domains may identify local network infrastructure.
- `get_network_manager_profile_ip` reads the saved IPv4 or IPv6 method, address/prefix list, and gateway for one exact profile UUID without requesting secrets. Runtime interface addresses may differ until the profile is applied.
- `get_network_manager_profile_routes` reads saved IPv4 or IPv6 route entries for one exact profile UUID, including destination, gateway, metric, and route attributes.

Destinations require an explicit prefix; metrics require a gateway. Replacement, duplicate destinations, multipath changes, and removal of routes with advanced attributes are refused. It changes only the saved profile and does not activate or reapply it; future profile application can affect traffic. Another NetworkManager client can race the final recheck; verification detects divergence but does not roll back the change.
- `configure_network_manager_profile_dns` changes selected saved IPv4/IPv6 DNS server lists, search domains, or automatic-DNS flags on one exact profile after confirmation bound to the current DNS state and requested values. An empty list clears that saved property; omitted properties are preserved. It validates literal IP addresses and DNS-domain syntax, requests no secret fields, and does not activate or reapply the profile.
- `configure_network_manager_profile_ip` sets one saved address family to automatic or manual mode. Manual mode requires literal address/prefix values and accepts one optional same-family gateway; automatic mode clears saved static addresses and gateway. The requested family state is bound to confirmation and checked after the update. It changes the saved profile only and does not activate or reapply it.
- `create_network_manager_virtual_profile` creates one persistent bridge, bond, or VLAN connection profile after confirmation bound to the complete profile inventory and interface identity. It starts inactive, has autoconnect and IPv4/IPv6 disabled, and does not attach bridge/bond ports. VLANs require an existing parent and an ID from 1 through 4094; bond modes use a fixed allowlist. Activating the profile later is a separate operation and may change network traffic.
- `create_network_manager_port_profile` creates an inactive Ethernet port profile attached to one exact saved bridge or bond UUID. Autoconnect is disabled, and the live interface is not switched. - `manage_network_manager_port_membership` attaches or detaches one exact pinned Ethernet profile from a saved bridge or bond profile. Attachment is limited to profiles with automatic IPv4/IPv6 methods and no saved addresses, gateways, DNS overrides, or static routes, because NetworkManager omits per-port IP settings while attached. Detaching leaves automatic methods and empty saved address/DNS/route lists. Autoconnect is preserved. The saved membership fields, complete profile inventory, and interface identity are rechecked. It does not activate, deactivate, or reapply either profile; an active profile keeps its applied settings until NetworkManager reapplies or reactivates it, and a later apply may change traffic.
- `import_network_manager_vpn_profile` imports one confirmed self-contained OpenVPN text file or a bounded wg-quick WireGuard config into a persistent inactive NetworkManager profile. OpenVPN inline credential blocks are accepted; known external file, include, management-socket, and helper-command directives are refused. WireGuard accepts only Interface/Peer settings from a strict allowlist, validates key/address/endpoint fields, and refuses shell hooks, file-based keys, and unsupported settings. It stages a private temporary copy, binds the full source content and complete profile inventory to confirmation, sets the profile name and autoconnect off, and does not query or return secrets. Inline certificates/private keys or WireGuard keys may be stored by NetworkManager; activation is a separate action.
- `list_systemd_network_profiles` parses bounded files beneath fixed systemd network configuration roots using a strict field allowlist, including `.network` DNS assignments, selected `UseDNS`/`UseDNR` flags, and `UseDomains` modes. It does not return raw file contents or secret fields such as WireGuard private keys or Wake-on-LAN passwords; symlink targets other than `/dev/null` are not followed, and overlapping files/drop-ins are reported as separate candidates without computing effective precedence.
- `configure_systemd_network_profile` edits selected DHCP, address/prefix, gateway, DNS, and virtual-link settings in one exact existing `/etc/systemd/network/*.network` file after confirmation. Address and gateway updates target `[Network]` directives; a separate `[Address]` or `[Route]` section makes that edit unavailable. It requires one literal `[Match] Name=`, refuses drop-ins and uncertain precedence, and accepts bridge/bond/VLAN membership only when each referenced `.netdev` is unambiguous. The full bounded config state is rechecked before replacement. Creation and deletion use their separate confirmed tools. It does not reload or reconfigure networkd; settings take effect when applied later, which may change routes or disconnect this client.
- `create_systemd_network_profile` creates one exact persistent `/etc/systemd/network/*.network` file with a literal interface match, explicit DHCP mode, and typed address, gateway, DNS/domain, DNS default-route, and bridge/bond/VLAN settings. It refuses filename collisions, target drop-ins, ambiguous earlier matching files, and unresolved virtual-device references. Creation requires the server to already run as root and writes the file with mode 0600. The complete bounded networkd state and generated file are bound to confirmation and rechecked after writing. It does not run `networkctl reload` or reconfigure the interface; a later reload or service restart can apply the profile and change routes, DNS, or connectivity.
- `create_systemd_netdev_profile` creates one exact mode-0600 `.netdev` definition for a bridge, bond, or VLAN. It supports bridge STP/VLAN filtering, one explicit Linux bond mode, or one VLAN ID from 1 through 4094; it refuses filename or live-interface name collisions and rechecks the bounded networkd state before and after writing. It requires the server to already run as root and does not reload or reconfigure networkd; a later reload or restart can create the interface and change connectivity.
- `configure_systemd_netdev_profile` updates bridge STP/VLAN filtering, a supported Linux bond mode, or one VLAN ID in an exact existing `.netdev` file. It preserves unrelated content, refuses duplicate target sections/directives, drop-ins, same-named fallback profiles, and ambiguous definitions, and binds confirmation to the file plus the complete bounded networkd state. `delete_systemd_netdev_profile` unlinks one exact inactive bridge/bond/VLAN definition only when no detected `.network` match or membership reference depends on it; it refuses drop-ins, same-named fallback profiles, and ambiguous networkd state. This is not secure erasure and has no recovery step. It refuses target drop-ins, uncertain precedence, and a same-named profile in another system configuration root because that profile could become active after deletion. Confirmation binds the full bounded network configuration, exact file identity, and current content digest; the tool rechecks them and verifies the path is gone. It does not reload or reconfigure networkd, so a later reload or restart may select another profile or leave the interface unmatched.
- `list_path_extended_attributes` lists visible xattr names and values for one explicit path, 128 attributes per page, with an 8,192-name scan cap, 4 KiB per-value previews, 32 KiB of raw attribute values per page, and 256 decoded ACL entries per attribute. ## Install and run

From the repository root:

```sh
uv sync --project wayland_mcp
uv run --project wayland_mcp linux-mcp
```

The legacy `wayland-mcp` launcher remains available for existing client configurations.

### Startup tool selection

All categories are enabled by default. Repeat these options in the server
command to hide categories or individual tools:

```sh
linux-mcp --disable-category networking
linux-mcp --disable-category networking --disable-tool list_processes
linux-mcp --disable-tool list_network_sockets --disable-tool list_socket_owners
linux-mcp --disable-category networking --enable-tool get_dns_configuration
```

The categories are `boot_kernel`, `command_execution`, `containers`, `desktop`,
`filesystem`, `hardware`, `networking`, `packages`, `power`, `processes`,
`scheduling`, `security`, `storage`, `system`, `users_identity`, and
`virtualization`. Run `linux-mcp --list-tool-categories` to see each category's
tools. The environment variables `LINUX_MCP_DISABLE_CATEGORIES`,
`LINUX_MCP_ENABLE_CATEGORIES`, `LINUX_MCP_DISABLE_TOOLS`, and
`LINUX_MCP_ENABLE_TOOLS` accept comma-separated lists. A tool assigned to more
than one category is hidden when any of those categories is disabled; an
environment enable entry clears the matching environment disable entry for
categories or tools, and command-line options are applied afterward.
`--enable-category` clears a matching environment category exclusion, while
`--disable-category` excludes that category even if it appears in the environment
enable list. An explicitly enabled tool, from the environment or command line,
overrides category exclusions, and a command-line tool choice overrides a matching
environment tool choice. The `command_execution`
category also includes `manage_cron_job` and `manage_at_job`: both schedule caller-supplied
shell commands for later execution. Disabling it hides these controls along with the
arbitrary shell and PTY tools; schedule inventory remains in `scheduling`.

`run_shell_command`, `start_terminal_session`, `read_terminal_session`,
`write_terminal_session`, `close_terminal_session`, `manage_cron_job`, and
`manage_at_job` also have `networking` membership because they can run or schedule
commands that inspect or contact network resources. Disabling `networking` hides
them unless they are explicitly re-enabled. `manage_container` and
`manage_container_pod` are shared because they can start workloads attached to
configured networks; `manage_virtual_machine` and `manage_virtual_machine_snapshot`
are shared because they can start or resume guests with configured network
interfaces. Startup selection controls tool registration; it does not sandbox
enabled tools or restrict operating-system access.

Disabling `networking` omits the dedicated interface, resolver, route, socket,
firewall, time-sync-source, and NTP settings/control tools, plus container-
network resource and attachment tools, container and image inventories whose
image references can disclose registry hostnames, `manage_container_image`
because pulls contact registries, `build_container_image` because builds can
fetch base images or run networked Dockerfile steps, the `create_container`
tool, which can publish ports or use an external volume driver, and package
transaction tools (`manage_package`, `manage_flatpak_package`,
`manage_snap_package`, `manage_nix_profile_entry`,
`manage_python_environment`, and `manage_native_package_environment`) because
they can fetch from configured repositories or registries. It also hides
libvirt-network and
remote libvirt-over-SSH tools, VM creation that attaches the guest to an existing
network, and local VM/guest lifecycle actions that can start or resume networked
workloads. The combined time-settings tool is hidden too, so its timezone
inspection/change functions also disappear.
It also hides `list_namespace_inventory` and `get_process_execution_context`,
which include network namespace identifiers, and `lookup_nss_identity`, whose
configured NSS source may be a remote directory.
The `networking` category also hides journal snapshots, fixed system-log
snapshots, Linux audit status/event/summary tools, and the generic audit watch
control because those records can contain peer addresses or hostnames and a
watch can target network configuration paths. Their capability readiness
entries are removed when all related tools are hidden.
It also hides `get_linux_system_info`, which returns the host name, and
`list_udev_devices`, whose generic device records can include network-interface
names and device paths. PCI/USB hardware inventory is shared too because class
codes can identify network adapters. SSSD domain inventory and control are
shared because they expose or change configured remote identity sources.
Current-session audio-server inventory and endpoint control are shared because
PulseAudio/PipeWire sinks or sources can be network tunnels. Bluetooth device
inventory and pairing are shared with
`networking`: the inventory reveals wireless-device names and addresses, and
pairing initiates a Bluetooth connection.
Some shared tools also manage volumes or storage pools, so those operations
disappear with the networking category too. Matching
readiness entries are hidden from `get_session_capabilities` when their tools
are disabled; a specifically re-enabled tool makes its entry visible again.
Mounted-filesystem inventory, fstab inventory, and the configured mount action
are shared with `networking` because network-backed mounts can expose remote
filesystem presence or activate a remote mount. The crypttab inventory is also
shared because its allowlisted `_netdev` marker can reveal network-backed
encrypted mappings. `manage_container_image` and `build_container_image` are
shared with `networking` because their pull/build operations may contact
registries or run networked build steps. `create_container` is also shared with
`filesystem` because it can mount host paths, and `build_container_image` is
shared with `filesystem` because it reads an explicit local build context.
The filter controls structured tools and is not a network-egress boundary:
workload starts and arbitrary shell or PTY commands may still access the
network through their own categories. Explicitly re-enabled network-tagged
tools remain available too. General system and
audit logs may contain network addresses, so disable `system` and/or `security`
if those log views are also out of scope. The filesystem category can read
explicit files, and the generic shell and PTY tools can run arbitrary commands;
disable `filesystem` and `command_execution` too when those access paths should
be unavailable; `command_execution` also disables the marked cron and one-shot at
controls that can execute caller-supplied commands later. Enabled desktop
observation tools may also show network data visible on screen. These filters
control which MCP tools are registered, not what an enabled general-purpose tool
can read or infer.

To run all Linux MCP tools with root permissions, configure the MCP client to launch the installed entry point through `sudo -n -- /absolute/path/to/linux-mcp`; the host's sudo policy must already permit that noninteractive command. This runs the whole server as root. `run_shell_command` with `run_as="root"` elevates only that one shell request. Root execution may not be able to use a user's desktop D-Bus or Wayland session.

The server runs until its MCP client closes stdin or the process receives a termination signal. It does not start Adam or a system service.

Example MCP client configuration:

```json
{
  "mcpServers": {
    "linux": {
      "command": "uv",
      "args": [
        "run",
        "--project",
        "/absolute/path/to/voice-assistant/wayland_mcp",
        "linux-mcp"
      ]
    }
  }
}
```

Start the MCP client from the graphical user session so it can access host procfs plus the Wayland socket, session D-Bus, compositor IPC socket, and portal permission flow. Environment forwarding is intentionally restricted to an allowlist.

## Suggested tool flow

1. Call `get_session_capabilities` to see which host features are ready or need permission/dependencies.
2. Call `list_windows`, `get_focused_window`, or `list_workspaces` and retain the returned `token_id`.
3. Use the exact returned ID and token for one corresponding action. If it expires or is consumed, observe again.
4. For keyboard, pointer, or touch input, use a fresh token whose observation shows the exact target focused. Pointer actions need verified window/output geometry; compositors with cursor readback verify the current cursor and resulting position, while Niri requires a selected ScreenCast monitor whose logical bounds match one current output. Touch actions require touchscreen permission and the same monitor-bound check; swipes require both endpoints inside the observed window.
5. Use `capture_screenshot` when visual evidence is needed. Read both the textual metadata and the returned MCP image block.
6. Call `observe_desktop` before clipboard or notification operations and pass its token to exactly one operation.

## Known limitations

- `run_shell_command` is the general command path for operations without dedicated structured tools. It runs arbitrary shell code only after exact-request confirmation, inherits the MCP process environment, uses pipes without a TTY, and has bounded runtime/output. Persistent PTY tools are available for interactive commands, and each input/resize requires its own confirmation. `run_as="root"` works only if the server is root or local sudo policy permits noninteractive execution. The active process identity and Linux security policy still govern every command, and detached processes may survive timeout cleanup. Startup category filtering removes selected tools from the schema; disabling `networking` also removes shared network-facing tools from the `system`, `filesystem`, `containers`, and `virtualization` categories, including the generic shell and PTY tools plus controls that launch configured containers or VMs. An explicitly re-enabled tool remains available. Generic filesystem and process tools may still reveal network-related data, and other enabled service controls may access networks. Use operating-system confinement or firewall rules when you need to enforce access restrictions.

- Radio inventory depends on kernel rfkill sysfs. Soft block/unblock control requires the optional `rfkill` command; it cannot change hardware/platform hard blocks, connect to networks, or configure saved wireless/Bluetooth profiles. Sysfs attributes are read as a non-atomic snapshot, and radio index reuse after revalidation is a narrow race.
- Local VM and libvirt resource support is limited to QEMU/libvirt resources accessible through fixed `qemu:///system` and `qemu:///session` URIs. Separate remote VM inventory and lifecycle tools accept only constrained `qemu+ssh` endpoints ending in `/system` or `/session`; they expose bounded remote snapshot inventory and confirmed disk-only creation for shut-off VMs, exact reversion, and leaf-only deletion, plus remote network and storage-pool inventory, selected volume metadata, and confirmed network/pool start-stop and autostart control. Standalone remote volume creation/deletion and remote domain configuration beyond stopped-VM memory/current-memory/vCPU updates remain unavailable. `create_remote_virtual_machine` creates a stopped remote VM with a new sparse qcow2 disk and optional existing persistent network; `attach_remote_virtual_machine_disk` attaches one existing raw/qcow2 volume to a shut-off remote VM after checking bounded domain definitions for reuse; `configure_remote_virtual_machine` changes memory/current-memory and vCPU values in a shut-off VM's persistent definition after binding confirmation to its full current XML and verifying the saved values. Remote SSH uses default keys and an owned agent socket, disables SSH config/agent forwarding/password prompts, and refuses unknown host keys. VM snapshots have a separate bounded inventory and confirmed create/revert/delete tool set; creation is limited to shut-off guests and deletion is limited to leaf snapshots. `create_virtual_machine` defines a stopped guest with a new sparse qcow2 disk and optional existing persistent network. `attach_virtual_machine_disk` adds one existing raw/qcow2 volume to a shut-off guest's persistent configuration after checking the visible local system/session VM definitions for disk reuse. Broader domain configuration beyond the bounded memory/current-memory/vCPU controls remains unavailable. `attach_remote_virtual_machine_disk` adds one existing raw/qcow2 volume from an active persistent remote directory pool to an unused virtio slot in a shut-off guest after checking remote VM definitions for disk reuse; it updates persistent configuration only and does not start the VM. `create_remote_virtual_machine` creates a stopped remote guest with bounded memory/vCPU, a new sparse qcow2 disk, and an optional existing persistent network, then verifies the saved definition; it does not install an OS or start the guest, and partial failure can leave the disk for inspection. Local and remote virtual networks and storage pools have bounded inventory plus confirmed network/pool start-stop and autostart control; selected remote pool volumes have bounded name and size metadata. `create_libvirt_storage_volume` creates only sparse raw/qcow2 volumes from 1 MiB through 1 TiB in persistent, running directory-backed pools; guest writes may overcommit pool storage. The creation tool does not attach its volume; the separate attachment tool requires a shut-off guest and supports only one unused virtio slot from vdb through vdz. Persistent inactive virtual-network definitions support isolated, NAT, routed, and existing-Linux-bridge modes. NAT/routed definitions require an explicit IPv4 bridge subnet checked against current host routes and addresses and can include a bounded DHCP range; bridge mode uses an existing host bridge. IPv4/DHCP updates are limited to supported inactive NAT/routed networks; other XML fields, IPv6, Open vSwitch, bridge/isolated edits, and forwarding-mode changes remain unavailable; pool/volume paths and XML, volume deletion, other hypervisors, and storage definition changes are also unavailable. `virsh` availability does not guarantee daemon connectivity or authorization, which are checked per request.

Resolver symlinks are followed only for a fixed set of common resolver-file locations; unknown targets are reported but not read. Nameservers, search domains, and interface names are local network metadata.
