# Linux MCP implementation notes

This file tracks implementation against the 12-area capability backlog. The [README](README.md) remains the user-facing guide and the canonical complete tool index.

## Scope and current state

`linux-mcp` is a standalone Linux MCP server in this repository. The implementation currently registers 266 structured tools across filesystem, host, desktop, network, storage, container, virtualization, identity, security, package, boot, hardware, and scheduling features. Coverage is intentionally bounded by each row below; partial coverage and the remaining work are stated explicitly.

`/etc/crypttab`, reporting mapping names, source classifications, key-source categories, explicit encryption modes, selected flags, and boolean PKCS#11/FIDO2/TPM2/keyscript indicators. Exact encrypted-device identifiers, key paths, and arbitrary option values remain hidden. `swap` and `tmp` settings are flagged because activation formats the mapped device and may erase existing contents. The tool does not read key material, unlock devices, or inspect active mappings; kernel-command-line and initramfs-only definitions may not appear in this file. `list_application_packages` reports Flatpak refs from the default system, configured named system installations, and the current-user installation, system-installed Snaps, and package names plus active state from the current user's default Nix profile; it omits Nix flake URLs and store paths and Snap publishers. Named Flatpak installations appear with scope `system_installation:<ID>`; pass that ID as `installation` with `scope="system"` to manage the ref. Inventory results are read-only and bounded; `manage_package` performs exact-package install/upgrade/remove or eligible system-wide upgrades through fixed manager arguments after explicit client confirmation, uses current OS permissions without elevation, withholds command output, reports timeout as potentially incomplete, and treats a zero manager exit status as success without a separate post-operation inventory check; separately documented host-control tools also require explicit confirmation. `sample_resource_history` returns aggregate/per-logical-CPU utilization and memory, swap, load, and uptime snapshots over at most 60 seconds; percentages are estimates from `/proc/stat` deltas, whose iowait field the kernel documents as unreliable. `sample_process_history` samples 2-20 times for up to 32 explicit PIDs over at most 60 seconds, derives CPU percentage from `/proc/PID/stat` user/system tick deltas, returns resident/virtual memory and thread count, and derives storage-layer read/write rates from `/proc/PID/io` byte-counter deltas. Those counters can be permission-limited, aggregate waited-for child activity, and do not represent cache-only read/write syscall traffic. CPU percentage is relative to one CPU and may exceed 100%; procfs start-time checks detect a replacement PID before it is mixed into the same history. `sample_cgroup_history` samples cgroup-v2 CPU use and throttling, memory and swap use/limits, and PID counts/limits for up to 32 explicit PIDs over 2-20 intervals and at most 60 seconds. Cgroup percentages are per one CPU and may exceed 100%; the tool checks process start time and exact cgroup membership around each sample, and only reports data when the same cgroup namespace and a verified `/sys/fs/cgroup` root are visible. `get_process_execution_context` reads the scheduling policy, priority, nice value, last CPU, CPU and memory-node affinity lists, cgroup hierarchy/controller/path membership, selected namespace inode IDs, `NoNewPrivs`, seccomp mode/filter count, and raw `CapEff` mask for one explicit PID. It reads no command line, environment, or working directory, bounds each procfs input, and checks start-time identity before and after collection. When the process shares the server process cgroup namespace and unified cgroup v2 is mounted at `/sys/fs/cgroup` with an unambiguous root, the tool also returns `cpu.max`, `cpu.weight`, cumulative `cpu.stat`, memory/swap limits and current usage, memory events, and PID limits/current counts for the process cgroup and up to 15 ancestors. These are cgroup snapshots, not rates; missing controllers or inaccessible files leave fields unavailable, and no cgroup files are written. Optional kernel fields may be absent or permission-limited. `list_gpu_devices` reads DRM card metadata from a bounded scan of `/sys/class/drm`. For `amdgpu` it reads documented busy-percent and VRAM attributes; for `i915` it reads card-level `temp1_input` and `energy1_input` from the exact `i915` hwmon device; for `xe` it reads package temperature, card/package cumulative energy counters, and actual frequency from each visible `tile#/gt#/freq0/act_freq`; and for `nouveau` it reads the documented `temp1_input`. Intel hwmon temperatures are converted from millidegrees Celsius to whole Celsius, while energy remains a cumulative microjoule counter and is not reported as a power rate. NVIDIA uses an optional fixed `nvidia-smi` CSV query for utilization, framebuffer memory, core temperature, and power draw; memory is converted from MiB to bytes and rows are matched to DRM cards by PCI address. Unsupported fields remain unavailable. The query requests no process data, UUIDs, serials, or controls, and does not inspect debugfs or writable power/performance controls. `get_process_tree` returns a bounded subtree rooted at one exact PID, with depth, scan, and result caps. `get_process_detail` returns an opaque token bound to the PID, UID, name, and procfs start time; `signal_process` requires that exact token and explicit client confirmation before sending one named signal. Linux pidfds are used when available; the compatibility path rechecks identity before `os.kill` but retains a narrow PID-reuse race on older kernels. `list_network_addresses` reports every visible IPv4/IPv6 address from `ip -j address show`, including secondary addresses and their scope, labels, flags, and lifetimes. `list_network_policy` reads the IPv4/IPv6 policy-routing database and routes from all tables via fixed `ip -j` show commands; `lookup_network_route` checks one literal destination with `ip route get`, sends no packets, and reports locally originated traffic using iproute2's default lookup context. Both require optional iproute2 and are bounded. `manage_network_route` adds or removes one exact transient unicast static route after explicit confirmation; add refuses to replace an existing destination/table/metric route, remove requires one exact protocol-4 route, and advanced/multipath routes are refused. It revalidates the route and interface index, fixes IPv6 preference to medium, verifies the result, uses current OS permissions, and never changes persistent network configuration. Default-route changes may interrupt this MCP connection. `list_firewall_rules` reads the active nftables JSON ruleset and IPv4/IPv6 `iptables-save` output from the current network namespace; it is read-only, bounded, may require permissions, and can show overlapping rules when iptables uses the nft backend. `list_firewall_frontends` reads firewalld runtime zone bindings/settings and UFW active state, defaults, logging, and displayed rules through fixed bounded commands; it does not query permanent firewalld configuration or change any firewall. Session inventory depends on `loginctl` and includes session ID, UID, username, seat, TTY, state, and idle flag; process IDs and remote host details are omitted. CPU frequency readings are point-in-time sysfs values and may describe a requested scaling frequency rather than a measured hardware clock; no frequency controls are exposed. `list_sensor_readings` scans bounded hwmon and thermal-zone input attributes, normalizes standard units, and includes raw readings plus a normalization status. Some hwmon temperature drivers report millivolts, and the hwmon ABI does not define a common humidity unit, so those readings remain explicitly marked as driver-specific; thresholds, alarms, and controls are excluded. `list_audio_devices` parses bounded `/proc/asound/cards` and `/proc/asound/pcm` snapshots for kernel ALSA cards and playback/capture PCM endpoints. `list_audio_server_devices` queries only `pactl info`, sink/source endpoint lists, or the equivalent `wpctl list audio sinks/sources`; it returns names, default endpoints, and available sink/source state, mute, and channel-volume metadata. `manage_audio_endpoint` changes one exact current-session sink/source volume (0-100%), mute state, or default endpoint after explicit confirmation; it binds confirmation to endpoint ID/name and current state, rechecks before execution, and verifies the resulting state. Volume/mute changes affect all clients using the endpoint; default changes may redirect new streams, and WirePlumber remembers its default selection across restarts. Command output is bounded and selected fields only are exposed; active stream/application metadata and audio content remain excluded. `list_power_inhibitors` calls logind `ListInhibitors` through fixed `busctl` arguments and returns bounded owner/reason strings, UID/PID values, affected operations, and modes; command lines and derived process names are omitted. `get_power_state` separately reports kernel sleep choices, which do not prove that firmware will complete a transition. `get_power_action_readiness` queries logind Can* results for one exact action, including CanRebootToFirmwareSetup where available; these indicate current support and authorization but do not predict hardware transition success. `manage_power_action` requires explicit MCP confirmation, calls fixed logind methods with interactive authorization disabled for poweroff, reboot, halt, and sleep actions, and uses fixed `systemctl --no-ask-password --no-block --firmware-setup reboot` arguments for firmware-setup reboot. Logind inhibitor locks are not bypassed; timeouts are reported as ambiguous because a transition may already have been accepted. `list_power_supplies` reads only a fixed allowlist of power-supply sysfs attributes and converts energy, charge, voltage, current, power, and temperature to Wh, Ah, V, A, W, and °C while preserving `online`'s raw state; manufacturer, model, serial-number, and writable charge-control fields are excluded. Filesystem inspection requires an explicit absolute path, follows the process's OS permissions, rejects paths under `/proc`, `/sys`, `/dev`, and `/run`, caps directory scans at 5,000 entries and text reads at 64 KiB, and performs no mutations. The separate `create_text_file` tool creates only new UTF-8 files up to 64 KiB with mode 0600 after explicit confirmation and never overwrites an existing target. `replace_text_file` replaces the full content of one regular UTF-8 file up to 64 KiB after confirming its current and replacement digests; it preserves file metadata by writing in place and attempts to restore original content after a write failure. ## Startup tool selection

Tools are filtered before MCP registration. The categories are `system`, `command_execution`, `processes`, `filesystem`, `networking`, `scheduling`, `boot_kernel`, `containers`, `virtualization`, `users_identity`, `storage`, `hardware`, `power`, `security`, `packages`, and `desktop`. A shared tool is hidden if any assigned category is disabled; `--enable-tool` is an explicit exception. This lets a client remove network-observation tools at startup, including cross-category tools whose output can disclose network-backed state. An explicitly enabled tool overrides category exclusion, so do not add `--enable-tool` exceptions for networking members when the category is meant to stay disabled.

Use repeatable `--disable-category networking` and `--disable-tool TOOL` arguments, or the comma-separated `LINUX_MCP_DISABLE_CATEGORIES`, `LINUX_MCP_DISABLE_TOOLS`, `LINUX_MCP_ENABLE_CATEGORIES`, and `LINUX_MCP_ENABLE_TOOLS` environment variables. `--list-tool-categories` prints category membership. `run_shell_command`, `start_terminal_session`, `read_terminal_session`, `write_terminal_session`, `close_terminal_session`, `manage_cron_job`, and `manage_at_job` also have `networking` as a cross-category membership because they can run or schedule commands that inspect or contact network resources. `manage_container` and `manage_container_pod` can start workloads on configured networks; `manage_virtual_machine` and `manage_virtual_machine_snapshot` can start or resume guests with configured network interfaces. Disabling `networking` hides these tools unless an individual tool is explicitly re-enabled. Startup selection filters MCP tool registration; it does not sandbox enabled tools or restrict operating-system access through other enabled tools.

`get_session_capabilities` reports readiness for each capability. Its selection-aware mapping omits readiness entries when all tools for that capability are hidden by startup selection.
